## 八、后续更新（9月17日–9月19日，第四阶段收尾优化）

报告初版（9月16日）之后，围绕会话管理体验与稳定性又做了以下改造，均已实测通过：

### 8.1 侧边栏按日期分组
- 会话列表由原来的固定 5 个时间桶（今天/昨天/前7天/前30天/更早）改为**按真实日期每天一个卡片框**：今天/昨天显示中文标签，更早显示「M月D日」。
- 每个 `.date-group` 框内会话竖向排列（HH:MM 时间 + 会话标题），由后端 `render_sidebar_html(user_id, current_chat_id)` 动态渲染。

| 用例 | 实测 |
|---|---|
| 跨天会话自动归入对应日期框 | 昨天 6 条、9月16日 5 条各自独立卡片 ✅ |
| 当前会话高亮（.active） | 切换后高亮跟随 ✅ |

### 8.2 会话删除与收起
- **删除**：每个会话项悬停显示 ×，点击后弹确认框，经 `delete_session` API 删除会话及其全部消息，删除后自动刷新。
- **收起/展开**：每个日期框标题前有 ▼/▶ 箭头，点击可折叠该天会话列表；收起状态用 localStorage（`date_collapsed`）持久化，刷新后保持。
- 实现上用 CSS class（`.date-list.collapsed{display:none!important}`）控制显隐，事件委托挂在 document 上，不与 Gradio 前端 Svelte 渲染抢 DOM。

| 用例 | 实测 |
|---|---|
| 点 × 删除会话并刷新侧边栏 | 通过 ✅ |
| 点 ▼ 折叠当天会话列表 | display:none 生效 ✅ |
| 刷新页面后收起状态保留 | localStorage 恢复 ✅ |

### 8.3 关键 Bug 修复
1. **点击旧会话后消息存错会话**：根因是 `select_session` 的 outputs 漏了 `chat_id`，只更新了聊天区显示、没把选中的 chat_id 写回前端 State，导致后续发言仍落到 bootstrap 时的旧会话。修复为 outputs 与返回值均补上 `chat_id`。实测：切到旧会话发消息，消息正确落入该会话且首条消息自动成为会话标题 ✅。
2. **前端白屏/长时间加载**：早期用 MutationObserver + 手动 appendChild 往 Gradio 的会话 DOM 注入删除按钮，与 Svelte 前端的 diff 机制互相冲突，导致 hydration 卡死、页面空白。改为纯 CSS 伪元素 + document 事件委托后白屏消失 ✅。
3. **`visible=False` 的 Radio 不渲染 DOM**：隐藏的会话 Radio 组件在 DOM 中不存在 input，JS 无法触发选中。改为组件常驻可见 + CSS `#conv-radio{display:none!important}` 隐藏 ✅。

### 8.4 启动与界面细节
- **启动预加载**：`__main__` 启动时先调 `get_backend()` 预加载 embedding 模型，避免打开页面时出现长时间 processing。
- **隐藏 Gradio 默认页脚**：通过 `footer_links=[]` 与 CSS 去掉「Runs · 由 Gradio 构建 · 设置」底栏。
- **按钮图标统一**：退出/上传/发送三按钮均使用白色 SVG 图标，尺寸与配色严格对齐阶段一参考图。

## 九、已知限制

1. 无账号密码登录（固定单用户，课程演示够用）。
2. 历史窗口为最近 5 轮（config.HISTORY_WINDOW 可调），超长对话不进 prompt。
3. 追问按钮固定 3 个槽位，推荐不足时自动隐藏多余按钮。
4. 多用户并发共用一份向量库/知识库（演示规模足够）。
5. 原始上传文件存于本地 `uploads/` 目录（见下方「附：本地存储与对象存储说明」），未接 S3/MinIO。

## 附：本地存储与对象存储的区别

阶段二原始要求提到「原始文件：对象存储（AWS S3/MinIO）」，本项目实际采用**本地文件存储**（`uploads/` 目录）。两者区别如下：

| 维度 | 本地文件存储（本项目现状） | 对象存储（S3 / MinIO） |
|---|---|---|
| 存储位置 | 服务器本地磁盘目录（`E:\...\uploads\`） | 独立的存储服务（S3 云 / 自建 MinIO） |
| 访问方式 | 直接读文件系统路径 `open(path)` | HTTP API：`PUT/GET/DELETE Object`，按 bucket+key 访问 |
| 适用规模 | 单机演示、几十个文件、几 GB | 生产环境、海量文件、TB 级、多机共享 |
| 扩展性 | 扩容要加磁盘、迁数据 | 水平扩容，节点自动负载均衡 |
| 高可用 | 单机磁盘坏了文件就丢 | 多副本/纠删码，自带冗余 |
| 多实例共享 | 多个后端进程看不到同一份文件 | 所有实例通过网络访问同一份数据 |
| 成本/复杂度 | 零成本、零部署 | 要部署 MinIO 或买云 S3，配密钥/桶权限 |
| 元数据 | 文件系统目录树 + SQLite | 桶/对象 key，配合数据库记映射 |

**本项目为什么用本地存储**：课程作业单机演示，文件量小（用户上传的课程 PDF/DOCX），用本地目录最简单可靠；`storage.py` 已抽象出 `make_object_storage()` 接口，将来要接 MinIO/S3 只需替换实现，不用改业务代码。若老师严格要求对象存储，本地起一个 MinIO 容器、把 `make_object_storage` 改成 S3 SDK 调用即可。
